# AI社員だけの課 設置計画書

## 0. この文書について

本書は、ENEOS社内に「AI社員だけで構成される課」を新設し、他部署からの依頼に対応できる組織・機能を構築するための計画書である。対象読者は、設置を検討する管理者、情報システム部門、および依頼元となる各部署の担当者を想定する。

本書はあくまで計画・設計段階の文書であり、実際の社内システム・機密情報へのアクセスを前提にしたものではない。実運用に進む場合は、情報システム部門・コンプライアンス部門による正式なセキュリティレビューと承認を別途経る必要がある。

関連ドキュメント:

- 組織体制の詳細: [org-chart.md](org-chart.md)
- 各AI社員の役割定義: [roles/](roles/)
- 業務フロー・ガバナンスの詳細: [processes/](processes/)
- 継続的改善サイクルの導入計画: [processes/continuous-improvement.md](processes/continuous-improvement.md)

## 1. 目的・背景

- 各部署で発生する「資料作成」「データ集計」「軽微なIT開発支援」「問い合わせ対応」などの定型的・反復的な業務は、担当者の時間を圧迫しやすい一方、完全な自動化（システム化）には至っていないものが多い。
- Claude Codeのカスタムサブエージェント機能を使い、これらの業務を一次受けする「AI社員」を課として組織化することで、依頼元部署は人手を介さずに（あるいは最小限の人手で）成果物の初版を得られるようにする。
- 目的は「人間の判断・承認を排除すること」ではなく、**人間が判断すべき部分に集中できるよう、下準備・一次対応をAIに任せること**である。最終責任・意思決定は人間が持つ前提を崩さない。

## 2. 対応する業務範囲

今回の課が「他部署からの依頼」として受け付ける業務は、以下の4分野に限定する。

| 分野 | 内容例 | 担当AI社員 |
|---|---|---|
| 資料作成・文書化 | 議事録整理、報告書ドラフト、提案資料の構成案、マニュアル作成・更新 | `ai-dept-docs` |
| データ分析・集計 | 社内データの集計、簡易レポート作成、グラフ化、傾向整理 | `ai-dept-data` |
| IT・システム軽微開発支援 | 社内ツールの簡易スクリプト作成、既存システムの調査・改善提案、ドキュメント化 | `ai-dept-itsupport` |
| 問い合わせ対応・一次窓口 | 他部署からの質問・依頼の受付、内容の整理、適切な担当への振り分け、FAQ的な回答 | `ai-dept-helpdesk` |

### 2.1 対応しない業務（明確化）

以下は本課の対象外とし、既存の人間の部署・プロセスに委ねる。

- 人事評価、契約締結、予算承認など、法的・人事的な最終決定を伴う業務
- 本番システムへの直接的な変更適用（コードやスクリプトの提案はするが、適用・デプロイは人間が行う）
- 機密情報・個人情報・取引情報を含む判断（詳細は[セキュリティ・機密情報の取り扱い](processes/security-and-governance.md)参照）
- 緊急度が高く、誤りが安全・法令・顧客対応上のリスクに直結する業務

## 3. 組織体制

課長（セクションリード）1名 + 専門AI社員4名という小規模体制とし、Claude Codeのカスタムサブエージェントとして実装する。各AI社員は固有の役割・ツール権限を持ち、課長が依頼の振り分けと成果物の整合性確認を行う。

```
                 ┌─────────────────────┐
                 │   課長（セクションリード）  │
                 │   ai-dept-lead         │
                 └──────────┬──────────┘
      ┌───────────┬─────────┴─────────┬───────────────┐
      │           │                   │                │
┌─────▼─────┐┌────▼─────┐   ┌─────────▼────────┐ ┌──────▼───────┐
│資料作成・文書化│ │データ分析│   │IT・システム支援     │ │問い合わせ一次窓口│
│ai-dept-docs  │ │ai-dept-data│  │ai-dept-itsupport │ │ai-dept-helpdesk│
└──────────────┘ └──────────┘   └──────────────────┘ └───────────────┘
```

各AI社員（サブエージェント）はClaude Codeの実行セッション（＝人間の管理者が操作する窓口）を介してのみ呼び出される。AI社員同士が直接・再帰的に呼び出し合う構成にはしない。これは、各ステップで人間が処理内容を確認できる状態を保つためである。

組織図・エージェント対応表・意思決定フローの詳細は [org-chart.md](org-chart.md) を参照。各役割の責務詳細は [roles/](roles/) 配下を参照。

### 3.1 人間の体制（必須）

AI社員だけの課であっても、以下の人間の役割は必須で配置する。

- **課の管理者（運営責任者）**: 課全体の依頼受付・振り分け実行・成果物のリリース判断を行う。実際にClaude Codeを操作し、各AI社員を呼び出す「オペレーター」も兼ねる。
- **レビュー担当**: 各分野の成果物を、依頼元に渡す前にレビューする。最初は管理者と兼任でよいが、業務量が増えた場合は分野ごとに割り当てる。
- **エスカレーション先**: 機密情報の判断、対象外業務の判定、AIの出力に疑義がある場合の最終判断者（情報システム部門・コンプライアンス部門など既存部署の責任者）。

人間による承認・レビュー体制の詳細は [processes/human-review.md](processes/human-review.md) を参照。

## 4. 業務フロー概要

1. 依頼元部署が、課の管理者（またはオペレーター）に依頼内容を伝える。
2. 管理者が `ai-dept-lead` を呼び出し、依頼内容を伝える。`ai-dept-lead` は依頼を分解し、対応分野・対応可否・必要な情報（機密情報の有無など）を判断し、「振り分け方針」を返す。
3. 管理者は方針に従い、該当する専門AI社員（`ai-dept-docs` / `ai-dept-data` / `ai-dept-itsupport` / `ai-dept-helpdesk`）を呼び出し、成果物のドラフトを作成する。
4. 人間のレビュー担当が成果物を確認し、必要に応じて修正指示を出す。
5. レビュー済みの成果物を依頼元部署に納品する。
6. 機密情報を含む、対象外業務に該当する、またはAIの出力に疑義がある場合は、いずれの時点でも人間（課の管理者またはエスカレーション先）が処理を止め、通常の人間の業務プロセスに切り替える。

詳細な受付フロー・判断基準は [processes/task-intake.md](processes/task-intake.md) を参照。

## 5. セキュリティ・機密情報の取り扱い（最重要事項）

本課が扱う情報の性質上、以下を計画の前提とする。詳細は [processes/security-and-governance.md](processes/security-and-governance.md) を参照。

- 機密情報・個人情報・取引上重要な情報は、現状の仕組み（Claude Code + 社外クラウド基盤経由のLLM利用）には**入力しない**ことを原則とする。
- 依頼を受け付ける際、`ai-dept-lead` および `ai-dept-helpdesk` は「機密情報が含まれるか」を必ず確認し、含まれる、またはその疑いがある場合は即座に人間にエスカレーションし、処理を継続しない。
- どの情報区分（公開情報／社内限定／機密）をAI社員に渡してよいかは、本課独自に決めず、既存の情報システム部門・情報セキュリティ部門の分類基準に従う。本計画の実行には、同部門との事前協議・承認が必須。
- すべての依頼・出力はログとして記録し、事後に追跡・監査できるようにする。

## 6. 人間による承認・レビュー体制

- AI社員の成果物は、**依頼元に渡る前に必ず人間が確認する**。AIが生成した内容がノーレビューで社外・意思決定に直結することはない。
- レビューの深さは業務分野によって変える（資料ドラフトは全文確認、簡易集計は数値の妥当性確認など）。詳細な基準は [processes/human-review.md](processes/human-review.md) に定める。
- 繰り返し精度の高い分野・依頼パターンについては、運用実績を見て段階的にレビューの軽量化を検討するが、初期フェーズでは全件レビューを必須とする。

## 7. 既存部署との役割分担・業務移行

- 本課は既存部署の業務を**代替・吸収する**ものではなく、既存部署からの依頼の「一次受け・下準備」を担う、という位置づけから開始する。
- 情報システム部門が持つシステム改修・運用業務や、各部署の最終判断業務はそのまま既存部署が持つ。本課はその前段のドラフト作成・調査・整理を支援する。
- 依頼元部署側の窓口（誰が本課に依頼を出すか）を明確にし、既存の問い合わせ先・ヘルプデスクと重複・混乱が起きないよう、案内・周知を行う。
- 業務量・実績が蓄積した段階で、どの業務をAI社員に正式移管するか、どの業務は人間が持ち続けるべきかを改めて評価する（フェーズ2以降、[processes/rollout-plan.md](processes/rollout-plan.md) 参照）。

## 8. 導入ステップ・費用対効果

段階的な導入計画とする。詳細は [processes/rollout-plan.md](processes/rollout-plan.md) を参照。

| フェーズ | 内容 | 目安期間 |
|---|---|---|
| フェーズ0 | 体制・ルール整備、情報システム部門との協議、対象業務の最終確定 | 1ヶ月程度 |
| フェーズ1 | 限定した協力部署1〜2部署とのパイロット運用（非機密業務のみ） | 1〜3ヶ月 |
| フェーズ2 | パイロット結果の評価、レビュー運用の見直し、対象部署の拡大 | 3〜6ヶ月 |
| フェーズ3 | 本格運用、対象業務分野の拡張検討 | フェーズ2評価後に判断 |

費用対効果は、AI社員1名あたりの処理可能な依頼数・リードタイム短縮・レビュー工数とのバランスで評価し、各フェーズ終了時に継続判断を行う。初期フェーズでは効果の定量化より、**事故が起きない運用の確立**を優先する。

## 9. リスクと今後の課題

- **誤情報・ハルシネーション**: AI社員の出力には誤りが含まれる可能性がある。レビュー体制の形骸化を防ぐ運用上の工夫が必要。
- **機密情報の誤入力**: 依頼元が意図せず機密情報を含めてしまうリスク。受付時のチェックと、依頼元への周知・教育が必要。
- **依頼の集中・切り分けの誤り**: 対象外業務が誤って本課に依頼されるケース。`ai-dept-lead` の受付判断と、人間の最終確認で防ぐ。
- **既存部署との責任の曖昧化**: 「AIが作ったから」を理由に人間の確認が疎かになるリスク。成果物には常に「AI社員によるドラフトであり、最終確認は人間が行っている」ことを明示する運用とする。
